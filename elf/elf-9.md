# ELF 的一些探索（九）：PIE 位置无关可执行文件及其汇编与加载调整

在第四、五、七篇中，我们看到的静态可执行文件（ELF Header 中的 `Type` 为 `EXEC`）有一个共同特点：**每一个段（`.text`、`.data`、`.rodata`、`.bss`）载入内存的虚拟地址，在编译链接结束的那一刻就已经彻底写死了**。内核 `load_elf_binary` 载入它时，也是老老实实地打上 `MAP_FIXED` 标志，原封不动地按 Program Header 规定的 `VirtAddr` 映射进内存。

按惯例，我们先来问一句：**这样写死地址有什么不好吗？**

从程序功能上来说完全没问题，但从**系统安全**的角度来说，这简直是灾难！因为不管这个程序在哪台电脑上运行、运行多少次，它的每一个函数、每一条指令、每一个全局变量在虚拟内存中的地址都是固定不变的。恶意攻击者只需要在自己的电脑上 `objdump` 一下你的程序，就能精确算出所有指令片段（Gadgets）和数据的固定地址，一旦程序存在栈溢出等漏洞，攻击者就能轻易实施内存攻击（如 ROP 控制流劫持）。

怎么防御这种攻击呢？科学家们想出了一个绝妙的主意——**如果在每次载入程序时，内核都随机生成一个偏移量 `bias`，把程序所有的段都在原有相对虚拟地址的基础上整体加上这个 `bias` 再映射进内存，攻击者不就猜不到真实地址了吗？**

这种可以加载到任意随机基址上运行的可执行文件，就叫做 **PIE（Position-Independent Executable，位置无关可执行文件）**。在今天的 Linux 系统中，`gcc` 默认编译出来的程序都是开启了 PIE 的。我们用 `readelf -h ./dynamic` 查看它的 ELF Header，会发现它的 `Type` 已经变了：

```text
ELF Header:
  ...
  Type:                              DYN (Position-Independent Executable file)
  Entry point address:               0x1080
```

那么问题来了：**当整个程序的所有段在加载时都被加上了一个随机偏移量 `bias` 后，我们的汇编指令还能正常跳转和访问变量吗？哪些地方不受影响，哪些地方必须修补？内核和启动代码又需要为此做哪些调整？**

---

## 1. PIE 的汇编技术：什么不用改，什么必须改？

### 1.1 PC 相对寻址的威力：代码跳转与本模块变量访问完全不用改！
细心读过第二篇《地址、立即数的管理和控制流的汇编》的小伙伴应该还记得，我们在讲 RISC-V 的 `auipc + addi` **PC 相对寻址**时埋下过一个重要伏笔：
> *“而且我们可以看到，只要指令和数据的相对偏移量保持一致，无论指令和数据的起始地址是多少，其实都是可以直接访问的，这个性质在之后可以起到大的用场。”*

现在，这个大用场终于来了！

当内核把整个 ELF 文件的所有 `LOAD` 段都统一加上同一个随机偏移 `bias` 载入内存时：
* 假设某条访存指令原来的相对地址是 `0x112a`，它要访问的本模块静态/全局变量 `time.0` 原来的相对地址是 `0x4030`。
* 加上随机偏移 `bias` 后，指令的真实地址变成了 `0x112a + bias`，变量 `time.0` 的真实地址变成了 `0x4030 + bias`。
* 你看，**它们两者之间的距离（相对偏移量）`(0x4030 + bias) - (0x1130 + bias) = 0x2f00` 根本没有发生任何变化！**

我们在 x86-64 的反汇编代码中可以清楚地看到这种基于 `%rip`（即 x86-64 的 PC 寄存器）的相对寻址：

```text
    112a:   89 05 00 2f 00 00       mov    %eax,0x2f00(%rip)        # 4030 <time.0>
    ...
    1139:   8b 05 f1 2e 00 00       mov    0x2ef1(%rip),%eax        # 4030 <time.0>
```

同理，本模块内部的函数调用（`call`）和分支跳转（`jmp` / `jne`）使用的也都是相对于当前 `%rip` 的偏移量。因此，得益于 PC 相对寻址技术，**整个 `.text` 代码段里的机器指令在开启 PIE 后一个字节都不需要修改**，天然就是位置无关的！

### 1.2 PIE 的软肋：数据段里存放的“绝对地址指针”怎么办？
既然代码段用 PC 相对寻址就能完美适应随机 `bias`，那是不是整个 PIE 程序什么都不用改就能直接跑了呢？

并不是！**指令可以用相对寻址，但存放在数据段里的“函数指针”或“数据指针”存的可是完整的虚拟地址！**

我们举个最直观的例子：在第七篇我们刚学过 `.init_array` 段（虚拟地址 `0x3da0`）和 `.fini_array` 段（虚拟地址 `0x3da8`），它们是两个**函数指针数组**，里面分别存放着初始化函数 `frame_dummy`（相对地址 `0x1160`）和析构函数 `__do_global_dtors_aux`（相对地址 `0x1120`）的入口地址。

在编译生成 ELF 文件时，编译器还不知道将来运行时随机生成的 `bias` 是多少，所以只能在文件里的 `0x3da0` 处先填上相对地址 `0x1160`。等到程序真正被加载到 `bias` 基址上运行时，`frame_dummy` 函数的真实地址已经变成了 `0x1160 + bias`！如果此时直接去读 `0x3da0 + bias` 内存里的函数指针并跳转，读出来的还是没加 `bias` 的 `0x1160`，一跳过去程序当场就崩溃了！

怎么解决这个问题呢？方法很简单：编译器在编译 PIE 程序时，会把所有这类**“需要在启动时加上 `bias` 偏移量的内存位置”**全部记录在一张清单里，这张清单就是 **`.rela.dyn` 重定位段**中的 **`R_X86_64_RELATIVE`** 表项！

我们用 `readelf -r ./dynamic` 看看 `.rela.dyn` 的前三条记录：

```text
Relocation section '.rela.dyn' at offset 0x5a0 contains 9 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000003da0  000000000008 R_X86_64_RELATIVE                    1160
000000003da8  000000000008 R_X86_64_RELATIVE                    1120
000000004008  000000000008 R_X86_64_RELATIVE                    4008
```

你看这三条 `R_X86_64_RELATIVE` 记录，它们不关联任何外部符号（`Info` 高 32 位符号索引为 `0`），意思直白得不能再直白了：
* 请在程序启动进入 `main` 之前，把偏移 `0x3da0`（`.init_array`）处的值改为 `0x1160 + bias`；
* 把偏移 `0x3da8`（`.fini_array`）处的值改为 `0x1120 + bias`；
* 把偏移 `0x4008`（`.data` 段里的一个指针变量）处的值改为 `0x4008 + bias`！

```text
+-----------------------------------------------------------------------------+
|                 PIE 程序的 R_X86_64_RELATIVE 基址重定位示意图               |
+-----------------------------------------------------------------------------+
|  [磁盘 ELF 文件中]                          [加载到内存基址 bias 后重定位]  |
|   Offset 0x3da0 (.init_array):               虚拟地址 (bias + 0x3da0):      |
|   +------------------------+                 +---------------------------+  |
|   | 0x0000000000001160     | ==(+ bias)===>  | bias + 0x0000000000001160 |  |
|   +------------------------+                 +---------------------------+  |
|   Offset 0x3da8 (.fini_array):               虚拟地址 (bias + 0x3da8):      |
|   +------------------------+                 +---------------------------+  |
|   | 0x0000000000001120     | ==(+ bias)===>  | bias + 0x0000000000001120 |  |
|   +------------------------+                 +---------------------------+  |
+-----------------------------------------------------------------------------+
```

### 1.3 `GNU_RELRO`：重定位完成后的“锁门”保护
我们再注意一个安全细节：像 `.init_array`（`0x3da0`）、`.fini_array`（`0x3da8`）以及后面要讲的 `.got`（`0x3fb0`），因为要在程序启动重定位时被写入加上 `bias` 后的真实地址，所以在它们所在的第 4 个 `LOAD` 段里，初始权限必须是可读可写（`RW`）的。

但是，一旦启动阶段的重定位填表完成了，在后续 `main` 函数运行期间，`.init_array`、`.fini_array` 这些函数指针表其实是**绝对不应该再被修改的**！如果一直保持 `RW` 可写权限，黑客一旦找到任意地址写漏洞，直接把 `.fini_array` 里的函数指针改成恶意代码地址，等程序退出时就会触发攻击。

为此，Program Headers 中专门设计了一个 **`GNU_RELRO`（Relocation Read-Only）** 段：

```text
Program Headers:
  Type           Offset             VirtAddr           PhysAddr
                 FileSiz            MemSiz              Flags  Align
  ...
  LOAD           0x0000000000002da0 0x0000000000003da0 0x0000000000003da0
                 0x0000000000000270 0x0000000000000278  RW     0x1000
  ...
  GNU_RELRO      0x0000000000002da0 0x0000000000003da0 0x0000000000003da0
                 0x0000000000000260 0x0000000000000260  R      0x1
```

可以看到，第 4 个 `LOAD` 段的范围是 `0x3da0 ~ 0x4018`（权限 `RW`），而 `GNU_RELRO` 精确覆盖了其中的 **`0x3da0 ~ 0x4000`**（正好包含了 `.init_array`、`.fini_array`、`.dynamic`、`.got` 这四个用于初始化和动态链接的段，而把 `0x4000` 开始的普通全局变量 `.data` 和 `.bss` 留在外面保持可写）。在启动阶段填完重定位数据后，启动代码就会根据 `GNU_RELRO` 的范围调用 `mprotect` 把这页内存从 `RW` 锁死成只读 **`R`**！

## 2. 支持 PIE 后，ELF 的 Load 与启动过程有哪些调整？

搞清楚了 PIE 的汇编与重定位原理后，我们回过头来看：为了支持 PIE，内核的 `load_elf_binary` 和用户态的启动初始化需要做哪些调整？

### 2.1 内核 `load_elf_binary` 的调整：加入随机 `bias` 与构造 `auxv`
1. **虚拟地址映射加上随机 `bias`**：
   在第七篇我们讲过，对于静态固定地址程序（`Type: EXEC`），`load_elf_binary` 直接按 Program Header 的 `VirtAddr` 打上 `FIXED` 标志映射；
   而对于位置无关的动态/PIE 程序（`Type: DYN`），为了更加安全、不容易被内存攻击，内核在载入 `LOAD` 段时，会在 Program Header 的虚拟地址基础上**加入一个额外的随机偏移量 `bias`**，然后调用 `elf_map` 将文件段载入到 `VirtAddr + bias` 的虚拟地址范围中。
2. **通过用户栈顶的 `auxv` 传递真实地址**：
   既然内核随机扔了个骰子生成了 `bias`，那程序回到用户态开始跑的时候，用户态代码怎么知道内核刚才生成的 `bias` 是多少、主程序的 Program Headers 被映射到了哪里、主程序偏移后的 `_start` 入口（`user_entry`）又变成了多少呢？
   答案是：**内核在返回用户态之前，会把这些关键信息打包成一系列 `(type, value)` 键值对（称为 `auxv` 辅助向量），连同 `argc`、`argv[]`、`envp[]` 一起压入用户栈的栈顶！**

以我们运行 `/home/zyy/system_security/env/dynamic` 程序为例，刚进入用户态时，堆栈栈顶（`%rsp` 指向处）的内存排布如下：
* 第一个 8 字节是 `argc` 的值（这里是 `1`）；
* 然后是 `argv` 数组，每 8 个字节是一个指向 `argv` 字符串的指针，长度为 `argc`，然后以一个 8 字节的 `NULL`（`0`）结尾；
* 之后依次是 `envp` 环境变量的字符串指针数组，最后也以一个 `NULL` 结尾；
* 再往后就是其他的内核辅助变量，也即 **`_dl_auxv`** 指向的地方；
* 而 `argv` 和 `envp` 的具体字符串内容，则依次排在 `auxv` 的后面，它们全都整整齐齐地躺在用户堆栈上！

```text
+-----------------------------------------------------------------------------+
|          程序启动刚进入用户态时的堆栈栈顶排布 (以 ./dynamic 为例)           |
+-----------------------------------------------------------------------------+
| 低地址 (栈顶 %rsp / arg 指向处)                                             |
|  +-----------------------------------------------------------------------+  |
|  | argc = 1                          (第 1 个 8 字节)                    |  |
|  +-----------------------------------------------------------------------+  |
|  | argv[0] 指针                      (8 字节，指向下方 "/home/zyy/...")  |  |
|  | NULL (0x0000000000000000)         (8 字节，argv 数组结尾)             |  |
|  +-----------------------------------------------------------------------+  |
|  | envp[0] 指针                      (8 字节，指向环境变量字符串 0)      |  |
|  | envp[1] 指针                      (8 字节，指向环境变量字符串 1)      |  |
|  | ...                                                                   |  |
|  | NULL (0x0000000000000000)         (8 字节，envp 数组结尾)             |  |
|  +-----------------------------------------------------------------------+  |
|  | _dl_auxv 辅助向量序列 (每项由 type 和 value 组成，内核 create_elf_tables)|
|  |   - AT_PHDR  : 主程序 Program Headers 在内存中的真实地址              |  |
|  |   - AT_PHNUM : Program Headers 的个数 (13)                            |  |
|  |   - AT_ENTRY : ★ user_entry (加上 bias 后跳入的 C 程序 _start 地址)   |  |
|  |   - ...                                                               |  |
|  |   - AT_NULL  : auxv 序列结束标志                                      |  |
|  +-----------------------------------------------------------------------+  |
|  | 字符串实体区:依次排列 argv[0..N] 和 envp[0..M] 的具体字符串           |  |
|  |   "/home/zyy/system_security/env/dynamic\0" ...                       |  |
|  +-----------------------------------------------------------------------+  |
| 高地址 (栈底)                                                               |
+-----------------------------------------------------------------------------+
```

### 2.2 用户态如何反推 `bias` 并完成重定位？
拿到了栈顶的 `auxv` 之后，用户态的启动代码（无论是静态 PIE 的自举代码，还是动态链接器 `ld.so` 的 `dl_main`）只需要做一件非常简单的事就能算出内核随机生成的 `bias`：

我们去遍历主程序的每一个 Program Header：当遇到第一个程序头 **`PT_PHDR`**（记录了 Program Header 数组自身的信息）时：
* 我们在 `auxv[AT_PHDR]` 里知道这个程序头此时**在内存中的真实位置**；
* 我们又能在 `PT_PHDR` 表项的 `VirtAddr` 字段里读到它在编译时**记录的相对起始位置**（比如 `0x40`）；
* **这两者的差值（`内存真实位置 - 记录的起始位置`），不就是内核给这个程序加上的随机偏移量 `bias` 吗！**

算出这个差值 `bias` 后，将它记录在管理结构 `main_map` 的 `l_addr` 字段中。之后：
1. 在计算 `DYNAMIC`、`INTERP`、`LOAD` 等各个段在内存中的真实起始和结束位置时，全都加上这个 `bias` 偏移；
2. 遍历 `.rela.dyn` 重定位表，把刚才我们看到的那些 `R_X86_64_RELATIVE` 表项所指向的内存地址全部加上 `bias`；
3. 最后把 `GNU_RELRO` 区间设为只读，PIE 程序就可以跟普通程序一样完美运行了！

## 小结
通过第九篇的探索，我们搞懂了 PIE 位置无关可执行文件是如何在“利用 PC 相对寻址保持代码段不变”的同时，通过 `.rela.dyn` 的 `R_X86_64_RELATIVE` 和内核 `auxv` 配合修正数据段指针的。

不过到目前为止，我们解决的还只是**“一个 ELF 文件内部的自我偏移修补”**。如果我们的程序不仅自身开启了 PIE，还要在运行时去调用外部共享库 `mylib.so` 和 `libc.so.6` 里的函数和全局变量，那又该怎么寻址和重定位呢？下一篇，我们就来全面攻克**动态链接技术与相关 ELF 段**！
